## 1. 结论与目标

PR 2 不改变七段任务流程，而是改变任务工具与命令的执行位置，减少 Agent 和仓库脚本对宿主机的直接影响。

当前结论：**有 Docker 基础代码，但尚未形成覆盖桌面任务的完整、任务级执行环境；旧方案需要校正后再实施。**

建议先验证“完整执行链路、会话恢复与停止行为”，再用数据决定性能退路。现有材料不能证明 macOS 挂载已经慢到不可接受。

本文区分三类信息：

- **已核实**：可以从当前源码确认的行为。
- **待验证**：原设计前提或跨容器运行风险，尚无本轮运行证据。
- **建议**：后续实施方向，不表示已经实现或得到新的产品决策确认。

### 需要纠正的旧表述

1. **“桌面端完全没接沙箱”不准确。** 桌面 Pi 会间接加载沙箱扩展；但存在入口不代表当前任务已正确绑定并进入容器。Qoder 则尚未接入容器启动器。
2. **“`execResult` 已是 SDK spawner 所需形态”不成立。** 前者返回执行完成后的结果 Promise；后者需要可持续通信的进程对象，包含 stdin/stdout、退出事件和 kill 等能力。
3. **“Router 生命周期直接上移 core”需要调整。** 当前 Router 依赖 integrations 的 `DockerSandbox`，而 integrations 已依赖 core。保留该依赖直接上移会形成循环依赖。
4. **性能退路仍是待验证决策。** 旧文档中的“三倍”是候选判断门槛，不是本轮实测结果。

## 3. 关键工作与边界

### 3.1 执行环境必须覆盖完整命令链

建议的职责划分：

| 位置         | 职责                                                                  |
| ------------ | --------------------------------------------------------------------- |
| 宿主机       | UI、数据库、任务编排、审批、Trace、Git 工作区准备、受控交付           |
| 任务容器     | Agent 的项目工具操作、setup、测试生成、lint/test/build 等项目执行命令 |
| 明确另行盘点 | OCR/Review 子进程、宿主 MCP、插件和其他能够执行项目代码的入口         |

不能只替换 Qoder 的启动方式：否则 Agent 在 Linux 容器执行，依赖安装和校验仍在 macOS/Windows 宿主执行，既有隔离缺口，也会产生依赖与平台差异。

涉及宿主专属工具链的任务，例如 macOS 原生构建，应明确判定不支持或采用可见的本机模式，不能隐式混跑后仍显示为“完整沙箱”。

### 3.2 任务级生命周期与 Pi 归属

建议把共享容器生命周期放在 `packages/integrations`，桌面层负责组装，Pi 层保留工具适配；不为此反转 core 的依赖方向。

- 容器、挂载与执行状态按 taskId 管理；不要继续依赖全局 `activeTaskId` 确定执行目录。
- 阶段实例会话继续遵循既有 fork/resume 设计；容器与会话的生命周期分别管理。
- 明确计划等待审批、暂停、失败重试、取消、应用退出和重启时的处理。
- Pi 某个阶段会话关闭不能意外销毁其他阶段或任务正在使用的容器。
- 状态应反映“实际启动成功”，而不是仅凭 `docker info` 成功显示沙箱已就绪。
- 容器清理必须按本应用管理的明确归属进行，不能操作无关容器。

参考：[任务阶段会话边界方案](./task-stage-session-boundary-plan.md)。

### 3.3 Qoder 进程适配

SDK 存在自定义 spawner 接口，但当前应用层尚未接通。需实现独立的流式适配，不复用一次性 `execResult()`。

验证清单：

- [ ] 容器内使用兼容的 Linux CLI，固定版本；不把宿主二进制路径原样当成容器命令。
- [ ] 正确传递 cwd、启动参数和经过筛选的环境变量。
- [ ] stdin/stdout 协议持续可用，多轮消息和错误输出正常。
- [ ] 启动错误、退出码和事件符合 SDK 的 `SpawnedProcess` 契约。
- [ ] interrupt、abort、close 与超时能够正确终止或保留对应会话。
- [ ] 取消后确认容器内工作进程停止；不能仅凭本机 `docker exec` 客户端退出判定完成。
- [ ] 运行时 transport、CLI 版本和实际执行位置可被 Trace 记录。

### 3.4 最小挂载、认证与会话

现有代码只挂 worktree。原方案提到的认证临时文件与会话目录问题需要针对当前 SDK 做实际验证，不应直接挂载整个用户目录解决。

| 资源       | 需要明确的契约                                                                                   |
| ---------- | ------------------------------------------------------------------------------------------------ |
| worktree   | 任务级白名单、必要的写权限、多仓库路径一致性                                                     |
| Git 元数据 | worktree 的 `.git` 指向主仓库元数据；只挂工作目录不足以保证 Git 可用。需设计最小可见范围与写权限 |
| 认证文件   | 容器可见的传递方式、生命周期、最小暴露范围，日志不得输出凭据内容                                 |
| CLI 会话   | 持久化位置、HOME/路径映射、宿主可观测性、阶段 fork/resume 与重启恢复                             |
| 阶段产物   | 明确通过提示词传入还是只读挂载；不为读取计划而暴露整个 dataDir 或数据库                          |
| 依赖与缓存 | 区分 Linux 与宿主平台产物，避免混用原生依赖；明确缓存归属与容器重建行为                          |
| MCP 与插件 | 盘点绝对路径、宿主服务地址与执行位置；容器里的 localhost 不等于宿主机                            |

禁止以“大范围可写挂载用户目录、凭据目录或主仓库”作为默认兼容方案。

### 3.5 权限与降级

**建议容器内外均保留 L1，而不是容器成功后只保留路径检查。**

原因：

- bind mount 内的删除和覆盖仍然影响宿主文件。
- 原方案网络取 `default`，并不提供外网、局域网或远端系统的访问隔离。
- 计划只读、测试阶段写入范围、敏感路径与交付边界仍是业务约束。
- 当前 L1 是应用层规则，不能替代操作系统级隔离，也不能据此宣称本机回退与容器等安全。

后续需要确认的降级策略：

- 推荐：请求沙箱的任务在沙箱不可用时暂停，用户明确选择本机模式后继续，保留 L1。
- 若保留原方案“自动回退本机”，应明确接受隔离能力下降，并保证执行前状态可见、记录原因及始终启用 L1。
- 不自动重放可能已产生副作用的失败命令；先区分“容器尚未启动”与“执行中失败”。

容器基线还应检查非 root 用户、资源限制、最小挂载和禁止暴露 Docker socket；这些在当前实现中尚未形成完整配置。

## 4. 建议跟进顺序

### A. 可行性验证：先跑通 Qoder 最小闭环

- [ ] 确认本机 Docker 可用、目标镜像及 CLI 版本；构建和真实模型调用前确认成本与环境影响。
- [ ] 在独立测试仓库验证容器内读写、Git 读取和一个最小项目命令。
- [ ] 验证认证、多轮、Plan → Implementation fork、同阶段 resume。
- [ ] 验证容器重建后的会话恢复与取消后的进程退出。
- [ ] 记录实际挂载、版本、结果与未通过项；不记录认证内容。

**退出条件：** 不依赖扩大宿主敏感目录挂载，最小会话链路和停止语义成立。否则先解决兼容性，不推进默认启用。

### B. 接通完整任务执行环境

- [ ] 提取任务级容器服务，避免 core/integrations 循环依赖。
- [ ] 接通 Qoder spawner 与 Pi 的显式任务归属、工具路由。
- [ ] 让 setup、实现和 lint/test/build 使用一致环境。
- [ ] 校验阶段交接、Review 自动修订后重测、多仓库和并行任务隔离。
- [ ] 保留宿主受控交付，盘点 Review/MCP 等剩余执行入口。
- [ ] 落地实际执行环境、镜像版本、降级原因和容器错误的可观测性。

**退出条件：** 不存在未声明的项目命令本机执行路径；任务切换和阶段关闭不会串用、误停容器。

### C. 性能评估与配置收尾

- [ ] 同一仓库、相同命令与相近缓存条件，对比本机与容器。
- [ ] 分别记录冷启动、热启动、文件检索/读取、依赖安装和 lint/test/build 耗时。
- [ ] 把模型响应时间与工具执行时间分开，避免用单次任务总耗时推断挂载性能。
- [ ] 多次运行后报告中位数及波动，再决定是否采用旧方案“三倍”门槛。
- [ ] 完成镜像入口、执行环境展示、失败提示和平台不支持提示。

Qoder 性能退路仍待选择：先调优挂载、接受额外耗时，或显式采用本机 + L1。Pi 虽具备工具级分流能力，但把读写留本机同样改变隔离边界，不能标成与完整容器等价。

## 5. 验收矩阵

| 场景                        | 预期                                                                     |
| --------------------------- | ------------------------------------------------------------------------ |
| 正常任务                    | 人工批准计划后，setup/实现/测试/校验在声明的同一环境执行，交付留宿主     |
| 阶段 fork 与重试            | 父会话、锚点及计划产物正确；权限随阶段变化，不串用旧会话                 |
| 容器重建或应用重启          | 会话与产物可恢复，恢复失败有明确原因，不假装续接成功                     |
| Docker 不可用或镜像启动失败 | 按已确认策略暂停或回退，执行位置可见，L1 保留                            |
| 执行途中失败                | 不盲目回退本机重放同一有副作用的命令                                     |
| 取消、超时、关闭            | 对应容器内进程确实停止，不影响其他任务                                   |
| 多任务、多仓库              | 目录、容器、会话与事件归属正确，不依赖全局活动任务切换                   |
| Git worktree                | 容器可执行任务所需 Git 读取，主仓库元数据未被过度暴露                    |
| 平台与原生依赖              | Linux/宿主产物不混用；不支持的工具链明确提示                             |
| 权限与数据保护              | 阶段限制、敏感路径与越界保护保持有效；不把 Docker 当作联网或远端操作授权 |
| 可观测性                    | UI 与 Trace 展示实际执行环境，认证信息不进入日志                         |

测试层次：进程适配/挂载/生命周期单测 → Docker 集成测试 → 真实任务手动验证 → 性能对比。Mock 测试通过不能替代容器内认证、Git 与会话恢复验证。

## 6. 实施前待确认

1. 沙箱失败采用“暂停并由用户选择本机”还是“可见地自动回退本机”？
2. 首批支持哪些平台和仓库工具链，如何标记无法容器化的任务？
3. 容器在等待人工批准、暂停与应用退出时保留多久？会话持久化不应依赖容器常驻。
4. 接受多大性能开销？先补数据，再选择 Qoder 的退路。
5. 宿主 MCP/插件等不在容器内的能力允许到什么范围，产品如何描述这一边界？
