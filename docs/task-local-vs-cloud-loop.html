1本地 Task 的实现（当前代码）

本地 Task 是一套跑在 Electron 主进程里的固定链路任务流水线：从任务创建、计划生成、人工审批、实现、测试、校验、Code Review，一路到 MR 提交与合并跟踪，全部由一个19 态状态机驱动，数据落在本地 SQLite，Trace 落在 JSONL 文件。

1.1 分层架构

图 1 · 本地 Task 分层架构：前端 / IPC / 主进程编排 / 共享包 / 本地存储，全部落在同一台机器

1.2 固定链路：19 态状态机

经过「Task 模式收缩」改造（docs/task-fixed-pipeline-plan.md），链路已从「9 组可配置组合」收缩为固定必经链路：计划审批恒为人工闸门，测试与 Review 恒为必经阶段（只允许结构性 no-op 且必须落事件留痕），任务级配置只剩「Review 通过后自动 / 手动提 MR」一个。

图 2 · 固定链路状态机：主链 12 个必经状态 + 人工闸门（计划审批）+ Review 自动修订回跳环 + 异常出口

异常出口：paused（手动暂停）/ awaiting_input（Agent 要补充信息）/ validation_failed / review_blocked（可自动修订回 implementing 循环）/ failed / cancelled。状态转移合法性由 core/workflow.ts 的 transitionTask() 硬校验，非法转移直接抛错。

1.3 核心模块职责

模块 位置 职责
TaskWorkflow integrations 阶段编排：建 worktree / feature 分支、跑 setup / validation 命令链、Review 收口；两条宿主（desktop 与 pi-package CLI 插件）共用
task-lifecycle.ts electron/task start / resume / pause / cancel / delete、计划生成与审批、runTaskOperation 在途操作管理（AbortController）、孤儿 Trace 收口
task-runner.ts electron/task Review 双路调用（Qoder SDK / OpenAI 兼容 HTTP）、Review 自动修订循环、测试覆盖检测、计划决策落库
双引擎 qoder / pi-session Qoder：常驻会话按 qoderSessionId 续接；Pi/OpenAI：全局单活 session。每个任务按 runtimeProvider 二选一
permissions.ts core L1 硬阻断（越出 worktree 的写、rm -rf、敏感路径等），两条引擎同源；任务侧 HITL 收敛为恒 yolo + L1 兜底
Trace / Memory electron 逐阶段 span 埋点（关键词提取 → Plan → Exec → CodeReview → …）落 JSONL；任务完成后记忆整理（consolidateTaskMemory）

1.4 关键执行机制

  • 在途操作管理：runTaskOperation(taskId, action) 用 Map 保存每个任务的 AbortController + Promise，新操作开始自动 abort 旧操作，保证同一任务同一时刻只有一条在途链路。
  • Review 自动修订循环：Review 阻断后按 reviewBlockingLevel 筛阻断意见，自动生成修订 prompt 回到 implementing，轮数受 reviewAutoFixMaxRounds（默认 2）约束。
  • 结论交叉验证：Agent 声称「已完成 / 无需修改」时，宿主用 taskChangedFiles()（git diff 对比 base 分支）复核，结论与文件改动不一致就不自动推进，落到人工确认。
  • 执行环境：本地 Git worktree（每任务每仓库独立 worktree + feature 分支），交付命令（commit / push / MR）留在主进程用宿主机凭据执行。

2云端 SaaS Task Loop 设计（docs/saas-architecture-plan.md）

SaaS 方案的核心决策：统一 Node.js 后端 + 可插拔执行环境 + 多租户。每个 Task 增加一个 executionTarget 字段决定执行位置，业务逻辑不感知执行位置： 

type ExecutionTarget =
  | { type: 'local' }                  // Electron 专属：本地 worktree 执行
  | { type: 'container' }              // Server 创建 Docker 容器执行
  | { type: 'queue'; loopId: string }  // Loop：异步队列执行（云端）

TaskWorkflow / QoderOrchestrator（业务逻辑，不感知执行位置）
        │
        ▼
  ExecutionBackend（统一抽象）
   ├── LocalBackend      → 本地文件系统 + execa（Electron）
   ├── ContainerBackend  → Docker 容器 FS + docker exec（云端）
   └── QueueBackend      → BullMQ 异步任务（Loop）
图 3 · 执行环境可插拔：业务逻辑与执行位置解耦，Loop 只是 executionTarget 的第三种取值

2.1 Loop 是什么

Loop 被明确定位为 Task 的上层编排，不是替代 Task 数据模型：实现「任务新增 → 任务计划 → 确认执行进入队列 → 任务完成」的异步流水线，仅需云端实现。技术选型 Redis + BullMQ（优先级队列、延迟任务、重试策略、并发控制、多 Worker 水平扩展）。 

interface TaskLoop {
  id: string; tenantId: string; name: string
  status: 'idle' | 'planning' | 'queued' | 'executing' | 'paused' | 'completed' | 'failed'
  concurrency: number                    // 同时执行的任务数（按租户配额）
  retryPolicy: { maxRetries: number; backoffMs: number }
  totalTasks: number; completedTasks: number; failedTasks: number
}

2.2 云端整体架构

图 4 · 云端 SaaS 总体架构：多端接入统一 API Server，PG / Redis 支撑多租户与队列，Docker Pool 承载任务执行
  • 执行环境：每任务一个 Docker 容器（非 root、只读根文件系统、网络白名单仅放行 npm registry / Git remote / LLM API、资源限额 2C2G），完成即销毁；基础镜像 + 依赖缓存卷把启动压到约 5 秒。
  • 多租户隔离：数据层 tenant_id 行级隔离（PG RLS 或应用层过滤）、执行层容器隔离、凭据加密按租户注入（不落镜像层）、LLM / 计算时长按租户计量配额。
  • 用户体验：Web 创建 Task / Loop → 秒级生成计划 → 审批后自动建环境（clone → 装依赖，进度可视）→ Agent 执行（实时日志流）→ 审查 diff / 测试结果 → 通过则 push + 建 MR + 销毁环境，要求修改则在既有环境继续。

3为什么本地 Task 存在局限

本地实现的所有限制，本质上来自同一个事实：任务的编排者、执行环境、数据和人工审批者全部耦合在同一台桌面机上。具体表现为六个方面：

3.1 任务生命周期与桌面进程绑定

Task 的驱动逻辑跑在 Electron 主进程里：activeTaskOperations、Pi 全局单活 session、Qoder 常驻会话都是进程内内存状态。合盖睡眠、退出应用、断电、崩溃，任务就停在原地，只能事后靠 resumeTask（仅 failed 态可续）或 sweepInterruptedTraces() 收口孤儿 Trace。单任务可达 10–30 分钟，全程要求这台电脑在线。

3.2 没有队列：串行、无调度、无重试策略

本地没有优先级、延迟任务、退避重试这些队列原语。一次只能实际推进一个活跃会话（Pi 全局单活），多个任务只能排着等人；任务失败后没有自动重试，需要人手动点「继续执行」。并发上限就是这台机器的 CPU / 内存 / 磁盘，跑一次 npm install + 全量测试会直接挤占用户的日常工作环境。

3.3 人工在环被假设「用户在场」

固定链路里计划审批是人工闸门，awaiting_input、Review 阻断上限后的遗留意见、手动档的 awaiting_commit 都等人。本地形态下这些等待没有通知机制——人不在电脑前，任务就永远停在那；也没有「审批完自动进队列、跑完推送通知」的异步闭环。

3.4 执行环境就是用户本机

安全边界目前靠 L1 正则拦断（越出 worktree 集合的写 / 破坏性命令 / 敏感路径）——这是应用层软边界，容器化沙箱（PR 2）已明确暂缓。Agent 理论上仍运行在拥有用户全部权限的环境里；同时本机的 ~/.ssh、凭据文件、其他项目目录都在同一文件系统上。桌面端的对策（每任务独立 worktree）只隔离了 Git 层，不隔离操作系统层。

3.5 数据与协作是单机孤岛

better-sqlite3 本地库 + JSONL Trace，无多端同步：换一台电脑任务历史就不可见；团队成员之间没有共享看板、没有配额与计量。产品价值中的「价值 A」（对话 / 计划 / 管理，天然适合云端）被锁死在桌面形态里。

3.6 原生能力反过来锁死了迁移

CodeGraph 索引、OCR、MCP / Skill 子进程都按「本地子进程」形态实现，Qoder 引擎的文件读写发生在 qodercli 子进程内部（只有进程级控制粒度），这些在架构上假设了「能碰到用户本机」，是后续云端化必须逐一适配的债务。

一句话概括：本地 Task 是「单人、单机、在场」模型——它把 IDE 级的交互体验（直接打开 VSCode、本地凭据、实时看板）做到了最好，但任务规模、并发、可靠性与协作的天花板就是这台桌面机本身。

4云端 Loop 的优势

4.1 异步流水线：审批之后不再需要人盯着

Loop 把「确认执行」和「执行完成」之间的整段变成无人值守：审批通过 → 自动进队列 → 建容器环境 → Agent 执行（实时日志流可看可不看）→ 完成等待 review → 推送通知。用户的参与点收敛为「批计划、审结果」两个决策动作，中间过程完全后台化。这直接消解了 §3.1 / §3.3 的局限——任务不再绑在任何人的电脑上。

图 5 · 用户参与时间线对比：本地任务要求机器与人全程在场，云端 Loop 把人收敛到两端的决策动作

4.2 队列带来的调度能力

  • 弹性并发：BullMQ Worker 多进程水平扩展，并发上限由租户配额（concurrency）控制，而不是某台电脑的资源。
  • 优先级与重试：紧急任务插队，失败任务按 retryPolicy（maxRetries + backoff）自动退避重试，替代本地「失败了等人来点继续」。
  • 削峰填谷：任务积压时排队而不是互相踩踏；夜间跑批成为可能。

4.3 更硬的安全边界

执行从「用户本机 + L1 正则兜底」变成「每任务独立容器 + 操作系统级隔离」：非 root 用户、只读根文件系统、网络白名单（仅 npm registry / Git remote / LLM API，禁止内网与其他租户容器）、资源限额、凭据运行时注入且容器销毁即清除。本地方案里暂缓的容器化（PR 2），在云端是必做基线。

4.4 多租户与团队化

tenant_id 行级隔离 + 认证 + 配额计量（并发任务数 / 存储 / LLM token / 计算时长），任务数据、Trace、MR 管理全部云端化，Web 端拿到全量能力，多人共享看板与任务流成为可能。这是从「个人工具」到「研发平台」的形态跃迁。

4.5 一套后端、一套数据模型

方案明确禁止演化为两套系统：Electron 与 Web 接同一 Server（本地部署时为本地内置 Server + SQLite），Loop 只是 executionTarget 的第三种取值，不动 Task 数据模型。桌面用户可以平滑地「把任务丢到云端跑」，本地与云端的 Trace / 记忆 / 看板天然同步。

维度 本地 Task（现状） 云端 Loop（设计）
执行驱动 Electron 主进程，进程内内存状态 API Server + BullMQ 队列，服务端持久化
用户离线后 任务停摆，需手动续跑 照常执行，完成后通知
并发与调度 单机资源上限，无优先级 / 重试 Worker 水平扩展，租户配额 + 优先级 + 退避重试
执行隔离 Git worktree + L1 正则软边界 Docker 容器硬隔离（网络 / 文件系统 / 资源）
数据 本地 SQLite + JSONL，单机孤岛 PostgreSQL 多租户，多端同步
计费 / 配额 无 LLM token、计算时长、存储按租户计量

5云端 Loop 的缺点

云端 Loop 不是免费的午餐，设计文档自己也把这些列为「潜在风险与应对」。归纳为六类：

5.1 工程与迁移成本高昂

  • 改造周期 12–16 周，五个 Phase（统一后端 API 化 → PG 多租户 → Docker 执行环境 → Loop 编排 → 计费运维），约 120 个 IPC endpoint 迁移为 HTTP + WS。
  • SQLite → PostgreSQL 是最大的隐性工作量：同步 API 换异步 API，波及所有 Store 调用点，上层业务代码需逐个 await 化。
  • Agent 执行链路适配面大：Qoder SDK / Pi Agent 的文件操作要经 ExecutionBackend 代理进容器；CodeGraph、OCR、MCP / Skill 子进程都要容器化或另想办法。

5.2 容器冷启动延迟与资源成本

每个任务 clone 仓库 + 安装依赖，裸跑可达 1–5 分钟；即便用「基础镜像 + 依赖缓存卷」压到约 5 秒，也引入了缓存卷管理、按租户 LRU 淘汰 repo clone 等运维负担。每任务一容器的模型在并发高时成本飙升，必须靠租户并发配额和同仓库容器复用来约束——成本模型从「用户的电费」变成「平台的账单」，且最终会转嫁给计费体系。

5.3 交互体验的折损

本地 Task 最好的部分恰恰是 Loop 给不了的：

  • IDE 联动丢失：本地任务可直接「在 VSCode / Qoder 中打开 worktree」，人在自己的环境里随手看代码、顺手改两行；云端容器里的代码只能通过 Web diff 查看。
  • 强交互阶段变弱：任务内追问（sendTaskMessage）、手动暂停 / 续跑、awaiting_input 补充信息这些「在场式」操作，在异步队列 + 通知的形态下变成「发起请求 → 等回调」。
  • 实时性：日志从本地 stdio 变成网络日志流，受网络与推送链路影响。

5.4 安全与信任责任上移

凭据（Git Token / Jira Token / LLM Key）从「用户本机加密文件」集中到云端入库加密，平台成为单一高价值攻击面；需要网络策略、审计、密钥不落镜像层等一整套纪律。更根本的是信任问题：私有代码必须 clone 到云端，企业内网仓库可能根本无法触达（容器网络只放行白名单）。对安全敏感的团队，「代码不出内网」是一条硬红线，云端 Loop 直接出局。

5.5 运维复杂度与新的故障域

Redis（队列）、PostgreSQL、Docker Executor Pool、镜像构建与 GC、配额中间件——每一个都是需要监控、备份、容量规划的基础设施组件。容器生命周期状态机（creating → ready → executing → destroying）与 GC 规则（完成 1 小时 / 空闲 30 分钟 / 失败 24 小时销毁）本身就是一个需要持续运营的子系统。本地版的「坏了重启应用」不再成立。

5.6 架构长期约束

  • 交付命令必须留在 host 侧（带宿主机凭据的 push / MR），执行与交付天然分裂在两个环境，链路更长。
  • 长任务依赖配额而非超时约束，租户配额体系一旦设计不当，要么限死大任务、要么成本失控。
  • Electron 本地模式不启用 Loop（可选连云端后使用），意味着产品要长期同时维护本地 / 云端两套执行路径的一致性——这正是「禁止两套系统」原则要持续对抗的引力。

6总结对照

本地 Task适合什么
  • 个人开发者，任务串行、追求 IDE 内闭环体验
  • 内网 / 私有仓库，代码不能出本机
  • 强交互任务：频繁追问、暂停改两行再继续
  • 零基础设施成本，开箱即用
云端 Loop适合什么
  • 任务批量化：审批后无人值守、夜间跑批
  • 团队 / 多租户：共享看板、配额、计量计费
  • 需要弹性并发与自动重试的规模化执行
  • 多端接入，Web 全量能力
结论：本地 Task 与云端 Loop 不是替代关系，而是同一套 Task 数据模型在两种 executionTarget 下的投影。本地形态的局限（单机绑定、无队列、软安全边界、数据孤岛）正是云端 Loop 的设计动机；而云端 Loop 的代价（12–16 周改造、容器成本、交互折损、代码上云的信任问题、运维复杂度）又恰恰是本地桌面形态的既有优势。SaaS 方案用「一套后端 + 可插拔执行环境」让两者共存，把选择权留给每个任务。
