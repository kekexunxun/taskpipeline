01 Agent 是什么 Concept

在 AI 领域，Agent（智能体）是一个能够感知环境、自主决策、执行动作的软件实体。 与普通的 LLM 对话不同，Agent 拥有：

🧠自主规划

接收一个高层目标后，Agent 能自主拆解为可执行的步骤（Plan → Implement → Test），不需要人类逐步指挥。

PlanningDecomposition

🔧工具使用

Agent 可以调用外部工具（文件读写、Shell 命令、MCP 服务、代码搜索等），通过工具与真实环境交互。

ToolsMCP

🔄持续会话

Agent 维护一个持久会话（Session），支持多轮对话、上下文记忆、中断恢复，而不是单次的请求-响应。

SessionResume
本项目中的 Agent 有两层含义：
① 运行时 Agent：由 Pi Agent Runtime 或 Qoder SDK 驱动的、正在执行任务的 AI 实体（拥有会话、工具、上下文）；
② 配置态 Agent（AgentProfile）：用户定义的领域角色，携带系统提示词、工程约定和模型偏好，任务执行时自动注入对应指引。

通用 Agent 系统架构（四层模型）

从通用视角看，一个完整的 Agent 系统可分为四层。这是行业通用的架构参考，后续章节会结合本项目具体实现做对照：

通用模型 vs 本项目：上述四层是行业通用的 Agent 架构参考。本项目的实现聚焦在编排层（Pi / Qoder SDK）和模型层（双运行时路由），通过 Pi Extension 机制把任务体系、工具、知识注入 Agent 运行时。后续章节会逐层展开。

四层架构详解

👤Layer 1 — 用户交互层

用户通过多模态输入与 Agent 交互：文本指令、语音命令、文件上传、图像识别。该层负责将各种输入形态统一为 Agent 可处理的标准消息格式。

在本项目中，交互入口是 Electron 桌面应用，通过 IPC 桥接与 Agent 后端通信，Chat / Coding 双页面对话式驱动任务。

多模态输入Electron IPC消息标准化

🎯Layer 2 — 编排层

主 Agent（总调度官）负责三大职责：

① 全局任务拆解（Plan & Decompose）— 将高层目标分解为可执行步骤
② 子 Agent 路由与委派（Routing）— 将子任务分配给领域专家
③ 多源结果融合与冲突仲裁（Fusion & Arbitration）

每个子 Agent（代码专家 / 数据专家 / 搜索专家 / 文案专家…）拥有独立的：

🧠 知识库（私有代码库 / 业务指标库…）· 🔌 MCP（Git/IDE / SQL/数仓…）· ⚙️ Skill（代码审查 / SQL 调优…）· 🔧 Tools（原子执行函数）

主 Agent 总调度子 Agent 专家化A2A 委派

🧠Layer 3 — 模型层

智能模型网关（Model Gateway）提供四大路由策略：

🔀 语义路由（意图识别，按任务类型选模型）
⚖️ 负载均衡（分散请求压力）
💰 成本控制（简单任务用小模型，复杂推理用强模型）
🛡️ 兜底降级（模型超时/报错自动切换备用）

支持接入：GPT-4o（最强推理）、Claude（长上下文）、Gemini（多模态）、DeepSeek（代码）、Qwen/Llama（本地部署）等。

语义路由成本感知故障降级

🏗️Layer 4 — 基础设施层

为整个 Agent 系统提供持久化与运维支撑：

📦 向量数据库（Milvus / Pinecone）— 知识库 Embedding 存储与检索
🗄️ 对象存储（S3 / OSS）— 文件与附件管理
📨 消息队列（Kafka / RabbitMQ）— 异步任务解耦
📊 日志 / 监控（Prometheus / Grafana）— 全链路可观测
🔗 外部 API — 第三方服务集成

向量存储可观测性消息队列

03 用户自定义 Agent User Guide

用户可以创建自己的 Agent（AgentProfile），为不同仓库/项目定制 AI 的行为风格。 Agent 的核心配置包括：

📝核心字段

name Agent 名称（如 "Java 服务端"）
systemPrompt 系统提示词：角色定位 + 领域知识
engineeringGuidelines 工程约定：实现前/中需遵守的流程
repositoryIds 绑定的仓库列表（单一归属）
preferredProvider 首选模型提供商
preferredModel 首选模型

🔗仓库单一归属

每个仓库只能绑定一个 Agent。保存时系统自动从其他 Agent 解绑同一仓库，避免冲突。

任务执行时，AgentService.resolveAgentContext() 按任务关联仓库找到对应 Agent， 把 systemPrompt + engineeringGuidelines + repowiki 注入到 Plan / Implementation / Test 全阶段。

自动注入全阶段生效

5.3 产品线 Agent 开发集成指南

基座建好之后，核心问题变成：产品线团队如何在基座上开发和集成自己的 Agent？
在"统一基座 + 多产品线"模式下，职责边界清晰：

🏗️基座平台团队

维护 Agent Runtime、模型网关、MCP 基础设施、权限审计等底层能力

RuntimeMCP 基础设施治理

🚀产品线团队

定义 Agent 行为（Prompt、知识库、MCP Server、Skill），无需关心底层编排和模型调度

Prompt知识库MCP ServerSkill

产品线团队的核心工作只有三件事：喂知识、接 MCP 工具、写 Prompt。完整流程如下：

🔌MCP 双层架构 — 业务能力基座

产品线接入业务工具时，以 MCP（Model Context Protocol）作为业务能力的基本单元。 MCP 天然支持双层架构，解决"全量工具注入导致上下文爆炸"的问题：

双层架构的核心价值：
Layer 1（领域 MCP Server）：每个业务领域聚合为一台 MCP Server，Agent 只看到领域级别的入口。 例如"订单域 MCP"对外只暴露"订单查询""物流追踪"等高层语义工具。
Layer 2（领域内工具）：具体实现细节封装在领域 MCP Server 内部，由 Server 自行路由到正确的子工具。 Agent 无需感知底层有多少细粒度工具。
效果：Agent 上下文窗口中只注入 4~8 个领域 MCP Server 的描述，而非 50+ 个散碎工具，彻底解决全量工具注入导致的 token 浪费和选择困难。

🔌MCP — 业务能力基座

产品线团队将自身系统的 API 封装为 MCP Server，遵循 MCP 协议标准。 每个领域一台 Server，内部封装该领域的全部工具能力：

🔹 按领域划分 MCP Server（订单域、库存域、财务域…）
🔹 Server 内部定义 tools / resources / prompts
🔹 高危工具标记 requires_approval，调用前自动走审批
🔹 Tool Gateway 自动处理鉴权、限流、日志、租户上下文注入

MCP 协议领域聚合按需暴露

⚡Skill — 关键节点补充

MCP 提供原子工具能力，而 Skill 补充跨领域编排和关键业务节点的逻辑：

🔹 Skill = 预定义的多步骤业务流程（如"退换货全流程"）
🔹 编排多个 MCP 工具的调用顺序和条件分支
🔹 嵌入人工确认节点、合规校验、异常回退
🔹 产品线团队用 YAML / DSL 定义，无需写 Agent 代码

关系：MCP 是"能力砖块"，Skill 是"流程蓝图"。Agent 优先调用 MCP 工具，遇到复杂流程时加载对应 Skill 获得编排指引。

跨领域编排关键节点流程蓝图

开发集成流程详解

📝① 定义 Agent Profile

每个产品线 Agent 是一份配置文件，描述身份、能力和行为边界：

🔹 system_prompt：角色定位 + 领域知识 + 行为规则
🔹 model_preference：模型偏好（网关实际路由决策）
🔹 permissions：可调用哪些领域 MCP Server、数据范围边界

Prompt 定义灵魂权限声明

📚② 接入知识库

产品线将领域文档灌入 RAG 知识库，无需关心向量化细节：

🔹 上传文档（PDF / Word / Markdown），指定 product_line 标签
🔹 配置切分策略：通用文档按 token 切分，FAQ 按 QA 对切分
🔹 混合检索（向量 + BM25）+ 重排序
🔹 多租户隔离：每个产品线独立 collection，查询时强制过滤
🔹 增量更新：文档变更自动重新切分、向量化、入库

RAG多租户隔离增量更新

🌐④ 接入渠道上线

Agent 通过基座接入层统一对外服务，产品线只需选择渠道：

🔹 Web：嵌入 JS SDK，传入 agent_id
🔹 企微/钉钉/飞书：基座已封装消息适配器，配置回调地址即可
🔹 OpenAPI：POST /v1/agents/{agent_id}/chat
🔹 App 内嵌：WebView 或 Native SDK

A. 轻量接入

06 总结 Summary

核心要点回顾：
  1. Agent 两层含义：运行时实体（Session + Tools）+ 配置态角色（AgentProfile）
  2. 通用四层模型：用户交互层 → 编排层（主 Agent + 子 Agent 专家集群）→ 模型层（智能网关路由）→ 基础设施层
  3. 四层解耦架构：Runtime → Extension → Orchestration → User Config，每层通过 DI 通信
  4. 用户自定义 Agent：空白创建 / 模板创建 / AI 生成，绑定仓库后全阶段自动注入指引
  5. A2A 委派：主 Agent 通过 SDK Agent 工具 spawn 子 Agent，形成 subtask.run → delegate tool → 子 Agent 内部 span 的嵌套结构
  6. 双运行时路由：Qoder（全功能主路径）+ Pi/OpenAI（灵活备选），resolveRuntime() 自动决策，模型失效保护
  7. 企业级五层实施架构：接入层 → 编排层（LangGraph）→ 工具与知识层（RAG + Tool Gateway）→ 模型层（LiteLLM）→ 基础设施与治理层（审计 + 评测）
  8. MCP 双层架构 + Skill 补充：领域 MCP Server（Layer 1）聚合工具，领域内工具（Layer 2）按需暴露，避免全量注入；Skill 补充跨领域编排关键节点
